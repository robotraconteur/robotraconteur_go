# Robot Raconteur Go bindings

[![CI](https://github.com/robotraconteur/robotraconteur_go/actions/workflows/ci.yml/badge.svg)](https://github.com/robotraconteur/robotraconteur_go/actions/workflows/ci.yml)
![license - apache 2.0](https://img.shields.io/:license-Apache%202.0-yellowgreen.svg)
![Go](https://img.shields.io/badge/Go-1.27+-blue.svg?style=flat&logo=go)
[![Go Reference](https://pkg.go.dev/badge/github.com/robotraconteur/robotraconteur_go/robotraconteur.svg)](https://pkg.go.dev/github.com/robotraconteur/robotraconteur_go/robotraconteur)

Go bindings for [Robot Raconteur](https://github.com/robotraconteur/robotraconteur).
They are built the way the C# and Java bindings are: SWIG wraps the C++ core
(using the core's shared `SWIG/*.i` files plus the Go interface in `swig/`),
and a hand-written Go runtime on top of it provides an idiomatic API.
`RobotRaconteurGenGo`, a stand-alone generator built with this repository,
generates Go packages from `.robdef` files. It uses the core's robdef parser
and verifier, so it accepts exactly what the other generators accept.

Version 0.1.1, for Robot Raconteur 1.3. Supported platforms: Linux (x86_64)
and Windows (x86_64, MinGW-w64). The native core is linked statically into
Go programs through cgo.

## Layout

| Path | Contents |
|------|----------|
| `robotraconteur/` | runtime package (`import rr "github.com/robotraconteur/robotraconteur_go/robotraconteur"`) |
| `robotraconteur/internal/swig/` | raw SWIG proxies (generated by `scripts/regen_swig.sh`, committed) and the `pkg-config` cgo directive |
| `native/gen/` | C++ side of the SWIG wrapper, one file per data model (generated, committed) |
| `swig/` | Go SWIG interface: `RobotRaconteurGo.i`, `shared_ptr`/`intrusive_ptr` support, typemaps, error plumbing, `postprocess_go.py` (see [swig/README.md](swig/README.md)) |
| `gen/` | `RobotRaconteurGenGo` (`GoServiceLangGen.cpp`, CLI in `main.cpp`) |
| `test/` | golden generator output, Go ports of the upstream test services and clients, loopback/interop/crosscheck tests (need generated packages, see [Testing](#testing)) |
| `examples/reynard_the_robot/` | Reynard client, simulated service, `go:generate` usage |
| `scripts/build_native.sh` | builds and installs the native libraries, the generator and `robotraconteur-go.pc` (see [Building](#building)) |
| `docker/`, `scripts/` | podman dev and MinGW cross images, development build/test scripts |
| `.github/workflows/ci.yml` | Linux CI; Windows cross build (Linux) and tests (windows-2022) |

## Building

### How it fits together

A Go program that uses Robot Raconteur is made of three parts:

1. **This module** (`github.com/robotraconteur/robotraconteur_go`): the Go
   runtime in `robotraconteur/`, plus the Go half of the SWIG wrapper in
   `robotraconteur/internal/swig/`. The SWIG output is generated once by the
   maintainers and committed, so users need neither SWIG nor Python.
2. **The native libraries**: the Robot Raconteur core (C++, with Boost) and
   `libRobotRaconteurGoNative.a` (the C++ half of the SWIG wrapper, committed
   in `native/gen/`). They are built once on your machine with
   `scripts/build_native.sh` and installed into a directory of your choice.
   Both are static libraries, so your Go programs do not need Robot
   Raconteur shared libraries at run time.
3. **pkg-config, the glue between the two.** The build script installs
   `lib/pkgconfig/robotraconteur-go.pc`, which holds the full link line. The
   internal package says `#cgo pkg-config: robotraconteur-go`. `go build`
   calls `pkg-config` and links your program against the installed
   libraries.

Why it works this way: `go get` downloads Go source and cannot run CMake.
cgo can compile small C files on its own, but not the core with its Boost
and OpenSSL dependencies. The native code therefore has to be built
separately and then located. Projects such as gocv (OpenCV) and govips
(libvips) solve the same problem with the same build-then-pkg-config
approach.

### Using the bindings in your program

**1. Install the prerequisites.**

- Go 1.27 or newer, a C++ compiler, CMake, Ninja (optional) and pkg-config.
- The core's dependencies:
  - Ubuntu/Debian:
    `sudo apt install build-essential cmake ninja-build pkg-config git libboost-all-dev libssl-dev libdbus-1-dev libbluetooth-dev libusb-1.0-0-dev`
  - Windows: see [Windows](#windows-mingw-w64) below.

**2. Build and install the native libraries** (about 10-20 minutes):

```sh
git clone https://github.com/robotraconteur/robotraconteur_go.git
cd robotraconteur_go
scripts/build_native.sh ~/.local/robotraconteur-go
```

The script downloads the Robot Raconteur core source and builds it as a
static library. By default it uses the commit CI tests,
`d8a4b228`: 1.3.0 plus #498 and the MinGW-w64 support of #497. It then builds this repository's native
library and the generator, and installs everything:

| Installed file | Purpose |
|------|---------|
| `lib/libRobotRaconteurCore.a`, `include/` | core library and headers |
| `lib/libRobotRaconteurGoNative.a` | C++ side of the Go bindings |
| `lib/pkgconfig/robotraconteur-go.pc` | link line used by cgo |
| `bin/RobotRaconteurGenGo` | generates Go packages from `.robdef` files |

These environment variables change what the script does:

| Variable | Default | Meaning |
|----------|---------|---------|
| `RR_SRC` | (download) | Use this Robot Raconteur core checkout instead of downloading one |
| `RR_GIT_URL`, `RR_GIT_REF` | `https://github.com/robotraconteur/robotraconteur.git`, `d8a4b228…` | Core repository and tag, branch or commit to download. The script stops if the fetch fails, and builds exactly the fetched commit |
| `BUILD_DIR` | `./build-native` | Build directory; it can be deleted after installing |
| `BUILD_TYPE` | `Release` | CMake build type |
| `JOBS` | number of CPUs | Parallel compile jobs. The SWIG wrapper is a very large file, so use 1-2 on machines with little memory |
| `PREFIX_PATH` | | Extra directories where CMake looks for dependencies, for example a Boost install (`;`-separated) |
| `CMAKE_ARGS`, `CORE_CMAKE_ARGS` | | Extra CMake arguments for both projects, or for the core only |

**3. Point pkg-config at the install.** Add these lines to your shell profile:

```sh
export PKG_CONFIG_PATH=$HOME/.local/robotraconteur-go/lib/pkgconfig${PKG_CONFIG_PATH:+:$PKG_CONFIG_PATH}
export PATH=$HOME/.local/robotraconteur-go/bin:$PATH   # RobotRaconteurGenGo, for go generate
```

Check that it is found:

```sh
pkg-config --libs robotraconteur-go
```

**4. Use the module as usual:**

```sh
go get github.com/robotraconteur/robotraconteur_go/robotraconteur
go build ./...
```

```go
import rr "github.com/robotraconteur/robotraconteur_go/robotraconteur"
```

Generate packages for your service definitions with `RobotRaconteurGenGo`
(see [Generating service packages](#generating-service-packages)).

**What gets linked.** Robot Raconteur itself is always linked statically. On
Linux, Boost, OpenSSL and the C++ standard library are the system shared
libraries (the same packages as above), as for any C++ program. On Windows
everything is static, including libstdc++, libgcc and winpthread, so
programs need only Windows system DLLs. Programs are large, about 30 MB,
because they contain the whole core.

**Upgrading.** Rerun `scripts/build_native.sh` with the same prefix after
updating this module or choosing a new core version. Go's build cache does
not notice when the libraries named in the link flags change. The `.pc`
file therefore carries a fingerprint of the installed archives
(`-DRRGO_NATIVE_FINGERPRINT=...` in `Cflags`), and a rebuild changes it, so
Go relinks your programs automatically.

**Versions.** The committed SWIG wrapper is generated from a specific core
version (currently 1.3.0, see `scripts/regen_swig.sh`). Build the native
libraries from that version, or from a later one that keeps the same SWIG
interface. A mismatch usually shows up as compile errors in
`native/gen/*/RobotRaconteurGo_wrap.cxx` while running `build_native.sh`, not later.

**Without pkg-config.** Build with `-tags rrgo_customenv` to leave out the
pkg-config directive, and pass the flags yourself:

```sh
export CGO_LDFLAGS="$(pkg-config --libs robotraconteur-go)"   # or write the flags by hand
go build -tags rrgo_customenv ./...
```

**Troubleshooting.**

| Message | Cause |
|---------|-------|
| `Package robotraconteur-go was not found in the pkg-config search path` | `PKG_CONFIG_PATH` does not include `<prefix>/lib/pkgconfig` |
| `pkg-config: exec: "pkg-config": executable file not found` | Install pkg-config (`pkgconf` on MSYS2), or use `rrgo_customenv` |
| `undefined reference to ...` while linking | The native libraries are out of date. Rerun `build_native.sh` |
| `cannot find -lboost_...` | The Boost packages are missing, or the system was upgraded after the native build. Install Boost and rerun `build_native.sh` |
| `invalid flag in pkg-config --libs` | A hand-edited `.pc` file contains a flag that cgo does not allow. Regenerate it with `build_native.sh` |

### Windows (MinGW-w64)

cgo needs a GCC-compatible C++ compiler on Windows, so the core and the
native library are built with MinGW-w64 rather than MSVC. The core
supports MinGW-w64 from
[robotraconteur#497](https://github.com/robotraconteur/robotraconteur/pull/497)
on. That change is not yet in a release (1.3.0 does not have it), but the
build script's default core commit includes it.

Native build with [MSYS2](https://www.msys2.org) (in the "MSYS2 MINGW64" shell):

```sh
pacman -S --needed git mingw-w64-x86_64-gcc mingw-w64-x86_64-cmake mingw-w64-x86_64-ninja \
  mingw-w64-x86_64-pkgconf mingw-w64-x86_64-boost mingw-w64-x86_64-go
scripts/build_native.sh ~/robotraconteur-go
export PKG_CONFIG_PATH=$HOME/robotraconteur-go/lib/pkgconfig
go build ./...
```

On Windows the script links Boost statically (`Boost_USE_STATIC_LIBS`).
CI cross-builds for Windows from Linux (below) and runs the tests on a
Windows runner. The native MSYS2 path above follows the same steps, but CI
does not run it.

### Developing the bindings

All development builds run in the podman dev image (Ubuntu 24.04, SWIG 4.2,
Go 1.27), using the same `build_native.sh` as a user build, installed into
`build/install`. The `robotraconteur` core checkout is expected next to this
directory (set `RR_SRC_DIR` to use another one) and is mounted read-only.

```sh
scripts/podman.sh image          # build the dev image (once)
scripts/podman.sh build          # core + native library + generators into build/install
RR_TESTING=ON JOBS=1 scripts/podman.sh build   # also the core's C++ test programs (interop tests)
scripts/podman.sh test           # golden test, go vet, go test ./... (no network)
scripts/podman.sh shell 'go test ./examples/...'
```

- **Build directories.** The core is built in `build/rr` and the native
  library and generator in `build/go`. Both are installed to
  `build/install`, and `scripts/test.sh` points `PKG_CONFIG_PATH` there.
- **Regenerating the committed sources.** Run
  `scripts/podman.sh shell scripts/regen_swig.sh` after changing `swig/*.i`,
  `swig/postprocess_go.py` or the core version. It writes:
  - `robotraconteur/internal/swig/robotraconteurswig.go` and `upcasts_gen.go`;
  - `native/gen/lp64/RobotRaconteurGo_wrap.cxx` and `.h` (`int64_t` is
    `long`: Linux, macOS);
  - `native/gen/llp64/RobotRaconteurGo_wrap.cxx` and `.h` (`int64_t` is
    `long long`: Windows);
  - `native/gen/rrgo_upcasts.cxx`;
  - `robotraconteur/errors_gen.go` and `constants_gen.go`.

  Commit the result. CI regenerates the files and fails if they differ from
  what is committed.

Windows cross build (the image adds MinGW-w64 and Boost 1.83 built for
MinGW to the dev image):

```sh
scripts/podman.sh mingw-image    # cross image, built on top of the dev image (once)
scripts/podman.sh build          # Linux build first: its generators are used by the cross build
scripts/podman.sh mingw-build    # core + native library into build-mingw/install
RR_TESTING=ON scripts/podman.sh mingw-build    # also the C++ test programs -> build-mingw/tests/cpp
scripts/podman.sh mingw-tests    # go vet, go build, test binaries and examples -> build-mingw/tests/*.exe
```

Copy `build-mingw/tests` to a Windows machine and run
`scripts/run_windows_tests.sh` there (Git Bash, from the repository root).

## Generating service packages

`RobotRaconteurGenGo` is built with the native library (`build/go/`) and
installed with it (`cmake --install`). It parses and verifies the robdef
files with the core library, like `RobotRaconteurGen`.

```sh
RobotRaconteurGenGo --output-dir gen \
    --go-import-prefix=example.com/myrobot/gen \
    -I robdef experimental.reynard_the_robot.robdef
```

Imported service definitions are found with `-I` and
`ROBOTRACONTEUR_ROBDEF_PATH`; pass them with `--import` to load them without
generating code, or use `--auto-import`. Errors are printed to stderr as
`file(line): error: ...`. `--thunksource` and `--lang=go` are accepted for
compatibility with the `RobotRaconteurGen` command line.

Each service definition becomes one package, with dots replaced by `__`: for
example `gen/experimental__reynard_the_robot`. `--go-import-prefix` is the
import path of the output directory, used when one service imports another.
`--go-runtime-import` overrides the runtime import path. The usual way to run
it is through `go:generate`; see
[examples/reynard_the_robot/generate.go](examples/reynard_the_robot/generate.go).

Generated code:

| robdef | Go |
|--------|----|
| `struct` | `*Name` (nil is null) |
| `pod`, `namedarray` | value structs; fixed arrays are Go arrays |
| `enum` | typed `int32` constants |
| `exception` | `*Name` error type wrapping `*rr.Error` (use `errors.As`) |
| `object` | interface `Name`, client stub, skel, `NameDefaultImpl` |
| `double[]`, `int32[*]`, `string{int32}`, `varvalue` | `[]float64`, `*rr.MultiDimArray[int32]`, `map[int32]string`, `any` |
| `property x` | `Get_x(ctx) (T, error)`, `Set_x(ctx, v) error` |
| `function f` | `F(ctx, args...) (ret, error)` |
| `objref o` | `Get_o(ctx[, index]) (Obj, error)` |
| `event e`, `callback c` | `Get_e() *rr.Event[func(...)]`, `Get_c() *rr.Callback[func(...) (..., error)]` |
| `pipe`, `wire`, `memory` | `Get_x()` returning `*rr.Pipe[T]`, `*rr.Wire[T]`, `rr.ArrayMemory[T]` / `MultiDimArrayMemory[T]` / pod memories |
| generator functions | `rr.Generator1[R,P]`, `Generator2[R]`, `Generator3[P]` (`Next(ctx, ...)`) |

Member names follow the C++ thunks: accessors are `get_`/`set_` plus the
member name unchanged (`Get_`/`Set_` so Go exports them), and functions
keep their name with the first letter upper case (`drive_robot` becomes
`Drive_robot`). Robot Raconteur reserves member names starting with `get_`,
`set_`, `async_` and `rr` (ignoring case), so these can't collide with each
other. Nor can they collide with the generated and runtime helpers, which
all start with `RR` (for example `RRBroadcaster_state` in a `DefaultImpl`).
The generated parameter for the context is `rr_ctx`.

## Node

A process has one Robot Raconteur node, `rr.DefaultNode()` (the core's
`RobotRaconteurNode::s()`), as in the C# and Java bindings.
`rr.ClientNodeSetup`/`rr.ServerNodeSetup` configure it, and the `*rr.Node`
values passed around the API all refer to it.

## Concurrency model

There is no separate asynchronous API. Every call that goes over the
network is a synchronous Go call taking a `context.Context`. Internally it
is the core's asynchronous operation awaited by the calling goroutine: the
goroutine parks on a channel, so no OS thread is held while a request is in
flight. Use goroutines for concurrency.

- **Timeouts.** A ctx deadline bounds each request, together with the node
  request timeout (`Node.SetRequestTimeout`).
- **Cancellation.** Cancelling ctx returns `ctx.Err()` immediately. The core
  can't cancel a request, so it finishes in the background. A late result
  that holds a resource, such as a connection or a pipe endpoint, is released.
- **Waits.** The `*Wait` methods (`ReceivePacketWait`, `WaitInValueValid`,
  `DefaultClientWait`) also wait on the goroutine.
- **Close.** `Close()` methods and `DisconnectService` take no ctx; they are
  bounded by the request timeout.
- **Service members run on their own goroutine.** The core's request
  thread is released at once, so implementations can block and make calls.
  `rr_ctx` describes the request (`rr.CurrentEndpoint`,
  `rr.CurrentServicePath`, `rr.CurrentServerContext`,
  `rr.CurrentAuthenticatedUser`). Objref lookups (`Get_o` on a service)
  and generator functions (the call that returns the generator) still run
  on the request thread, so they should return quickly; the generator's
  `Next`, `Abort` and `Close` run on their own goroutines.
- **Inline callbacks.** Events, callbacks, wire and pipe notifications and
  timers run on core threads. They should return quickly; requests made
  from them hold that thread until they complete.
- **Thread-pinning exceptions.** Memories and monitor locks
  (`WithMonitorLock`) still hold an OS thread for their duration.

## Client

```go
setup, err := rr.ClientNodeSetup(rr.WithServiceTypes(reynard.Factory))
if err != nil { ... }
defer setup.Close()

ctx := context.Background() // or a context with a deadline / cancellation
obj, err := setup.Node.ConnectService(ctx, "rr+tcp://localhost:29200?service=reynard")
if err != nil { ... }
defer setup.Node.DisconnectService(obj)
c := obj.(reynard.Reynard)

c.Get_new_message().Connect(func(msg string) { fmt.Println(msg) })
if err := c.Teleport(ctx, 0.1, -0.2); err != nil { ... }
state, ts, err := c.Get_state().PeekInValue(ctx)
```

Wires, pipes, memories, object locks (`Node.RequestObjectLock`, `WithMonitorLock`),
subscriptions (`Node.SubscribeService`, `SubscribeServiceByType`,
`SubscribeServiceInfo2`, wire/pipe subscriptions and
`ServiceSubscription.SubscribeSubObject` for objref targets such as
`"*.o1.o2_1"`) and local-transport discovery are supported.

Transports come from `NodeSetup` (`TCPTransport`, `LocalTransport`,
`IntraTransport`, `HardwareTransport`). For a node configured by hand, use
`rr.NewTCPTransport(node)` (and `NewLocalTransport`, `NewIntraTransport`,
`NewHardwareTransport`) followed by `Node.RegisterTransport`.

## Service

Embed the generated `DefaultImpl` and override what you implement. Then
register the object:

```go
type robot struct{ reynard.ReynardDefaultImpl }

func (r *robot) Teleport(ctx context.Context, x, y float64) error { ... }

setup, err := rr.ServerNodeSetup("experimental.reynard_the_robot", 29200,
    rr.WithServiceTypes(reynard.Factory))
ctx, err := setup.Node.RegisterService("reynard", "experimental.reynard_the_robot.Reynard", &robot{})
```

Other service-side features:

- **Readonly wires and pipes.** These get broadcasters in the `DefaultImpl` (`RRBroadcaster_state`). `rr.NewBroadcastDownsampler` adds per-client downsampling.
- **Security.** Pass `rr.WithSecurityPolicy(&rr.ServiceSecurityPolicy{Authenticator: rr.NewPasswordFileUserAuthenticator(data), Policies: ...})` to `RegisterService`. Authenticators can also be Go functions (`rr.UserAuthenticatorFunc`) that return an `*rr.AuthenticatedUser` or an error. Unlike the C++ and Python bindings, `requirevaliduser` defaults to `"true"` when `Policies` does not set it; set it to `"false"` to also allow anonymous clients. An `*rr.Error` returned without a `Code` is sent as `UnknownError`, never as success. Service members can call `rr.CurrentAuthenticatedUser(ctx)` and `rr.CurrentServerContext(ctx)`.

## Memory management

Native handles of long-lived objects are freed by `runtime.AddCleanup` once
the Go object is unreachable. These are stubs, pipe endpoints, wire
connections, generators, subscriptions, broadcasters, timers and memory
clients. `Close`, `DisconnectService` and subscription `Close` only perform
the native close; the core then releases the object's callbacks, which
makes the Go object collectable. Native messages never reach user code:
they are converted to Go values and freed immediately.
`rr.NativeHandleCount` reports live handles, for leak tests.

## Errors

Failures are returned as Go `error` values. Network, transport, remote and
framework errors never panic.

- Built-in errors are `*rr.Error{Code, Name, Message, SubName, Param}`, with
  sentinels for `errors.Is`: `rr.ErrConnectionError`, `rr.ErrTimeout`,
  `rr.ErrInvalidArgument`, and so on.
- Constructors for service implementations: `rr.NewInvalidArgument("...")`, and the others.
- Service-defined exceptions are generated types, matched with `errors.As`.
- A service member returning an `error` sends it to the client. A panic in a
  service member, or in any other callback that C++ invokes, is recovered and
  becomes `RobotRaconteur.UnknownError`.
- Panics are kept for programmer errors, such as a nil receiver.

## Logging

```go
node.SetLogLevel(rr.LogLevelDebug)            // or SetLogLevelFromString / SetLogLevelFromEnv
node.SetLogRecordHandler(func(r rr.LogRecord) { log.Println(r) })
node.OpenLogFile("rr.log", true)
```

## Timers

`Node.CreateTimer(period, oneshot, func(rr.TimerEvent, error))` and
`Node.CreateRate(hz)` follow the node's time base, unlike `time.Ticker`.
They matter when a custom time provider is installed (simulation).

## Testing

**Generated packages.** The packages under `test/` and
`examples/reynard_the_robot/` import Go packages generated from `.robdef`
files: `test/gen/` and `examples/reynard_the_robot/gen/`. Generated code is
not committed, so in a fresh clone (and on pkg.go.dev) those packages do not
build until it is generated. The `robotraconteur` package itself does not
depend on them. `scripts/test.sh` (and so `scripts/podman.sh test`) runs
`scripts/gen_test.sh` first. Outside the dev container, with
`RobotRaconteurGenGo` on `PATH`:

```sh
(cd examples/reynard_the_robot && go generate)
RobotRaconteurGenGo --go-import-prefix=github.com/robotraconteur/robotraconteur_go/test/gen \
    -I <robotraconteur source>/test/robdef --output-dir test/gen \
    com.robotraconteur.testing.TestService1.robdef com.robotraconteur.testing.TestService2.robdef \
    com.robotraconteur.testing.TestService3.robdef com.robotraconteur.testing.TestService4.robdef \
    com.robotraconteur.testing.TestService5.robdef
RobotRaconteurGenGo --go-import-prefix=github.com/robotraconteur/robotraconteur_go/test/gen \
    --output-dir test/gen test/robdef/experimental.gen_test_go_names.robdef
cp <robotraconteur source>/test/data/test_vectors.bin test/testvectors/
```

`scripts/podman.sh test` runs in a container with `--network=none`. Only
loopback TCP, local and intra transports are used, and network discovery is
not enabled. The tests cover:

- `test_gen_go`: `RobotRaconteurGenGo` output for TestService1-3 is compared with `test/golden/` (update it with `scripts/update_golden.sh`).
- `test/loopback`: Go service with a Go client in one process.
- `test/interop`: the Go ports of `ServiceTestClient` and `ServiceTestClient2`, plus subscription tests, against the upstream C++ `robotraconteur_test_server`.
- `test/crosscheck`: the upstream C++ client test programs, plus the Go clients, against the Go ports of the test services.
- `examples/reynard_the_robot/client`: the example client against the simulated service.

The interop and crosscheck tests need `RR_TESTING=ON` builds. Without the C++
test programs they skip.

On Windows, CI runs the cross-compiled test binaries for every package,
including interop and crosscheck against the C++ test programs cross-built
with MinGW-w64. The Go tests start those programs with node discovery
disabled, because a CI runner is not isolated like the dev container.

## Not yet supported

- macOS. The runtime is OS-neutral, but the core and toolchain setup for cgo has not been done.
